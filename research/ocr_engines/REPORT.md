# Распознавание маркировки деталей: сравнение OCR-движков

Октябрь 2026, плата `out/captured_51.5`. Все движки стоят в своих venv под `research/ocr_engines/venvs/`.
Проектный `venv/`, код проекта и `markings.json` не трогал.

## Коротко

- **Победитель — Qwen3-VL-2B-Instruct** (VLM на 2B параметров, Apache-2.0, 4 ГБ весов) через `transformers`.
  - На 116 деталях с эталонным чтением при известном развороте: **90 точных совпадений** на вырезке `parts/`, **92** на вырезке из самого резкого исходного кадра.
  - Голосование «панорама + лучший кадр + медиана кадров» даёт **93/116**, ещё 9 расходятся на один символ.
  - Для сравнения: текущий RapidOCR (PP-OCRv3) — 37, лучший классический OCR — 63.
  - На 40 деталях без маркировки — **0 ложных чтений**.
  - Скорость: **0,26 с на чтение на RTX 5080** и ≈7 с на CPU (4 потока, fp32); точность на CPU та же (на контрольных 24 деталях 17/24 в обоих случаях).
- По группам:
  - **резисторы 79/80** (CER 0,01; единственное расхождение — R44, см. «Находки»);
  - C/L/X 7/14 точно и 13/14 с точностью до символа;
  - **микросхемы только 4–6/17** (CER ≈0,32): слабая лазерная маркировка упирается в изображение, а не в движок.
- GPU есть: **RTX 5080, 16 ГБ, драйвер 581.42 / CUDA 13.0**. Работает с PyTorch 2.14.1+cu130; колёса cu128 для cp313 есть только до torch 2.11.
- Дешёвый апгрейд без GPU и PyTorch: `rapidocr` 3.10 (та же ONNX-обвязка) с моделями PP-OCRv5 server на `parts/` — **63/116**, 1,7 с на чтение.
  EasyOCR с белым списком символов даёт 59–62/116 при 0,35 с, но почти только на резисторах.
- Tesseract, docTR, TrOCR — непригодны (1–18/116). MMOCR не ставил: не поддерживается с 2022 года, mmcv не собирается под Python 3.13/Windows.
- **Найденная ошибка в `ocrMarkings.turn()`** (обнаружила соседняя сессия; к 12:10 в `ocrMarkings.py` исправлено).
  `cv2.ROTATE_90_CLOCKWISE == 0`, поэтому поворот на 90° был пустой операцией.
  Мой первый прогон импортировал эту функцию: все строки с поворотом 90° и 10 резисторов с `turn` 90 были неверны.
  Харнесс теперь использует свой `turn()`, затронутые 5 740 чтений пересчитаны; цифры ниже — после исправления.
  Сводка в `markings.json` (`same 28 …`) посчитана ещё со старым «перебором 4 поворотов», который на деле был 0, 0, 180, 270.

## Данные и метрика

- 116 деталей, у которых в `markings.json` есть `lines`: 80 резисторов, 17 микросхем, 5 диодов и транзисторов, 14 C/L/X.
  Отдельно взяты 40 деталей без маркировки (каждая третья) — по ним считаются ложные чтения.
- Источники (все повёрнуты эталонным `turn`):
  - `raw` — `parts/<ref>.jpg`, цвет;
  - `mimg` — `marking_img/` (серый + CLAHE + увеличение);
  - `body` — только корпус по контуру из CAD, CLAHE, ≈480 px;
  - `frame` — та же вырезка, но из самого резкого (дисперсия лапласиана) исходного кадра `sources/`, без многополосного смешивания;
  - `fmed` — попиксельная медиана по всем кадрам, где корпус виден целиком.
- **Разворот задан**: поворот 0 от эталонного. **Разворот неизвестен**: 4 поворота, побеждает поворот с максимальной средней уверенностью, как в `ocrMarkings.py`. Оракул — «верен хотя бы один поворот».
- Метрики:
  - **точно** — `ocrMarkings.agree == "same"` (после свёртки похожих символов O/0/D, I/L/1, S/5, B/8, Z/2, G/6);
  - **±1** — `same` + `close`;
  - **CER** — расстояние Левенштейна между свёрнутыми строками, делённое на длину эталона; пустой ответ даёт 1.
- **Оговорка про эталон.** Эталон — чтение другой vision-моделью, а не проверенная истина.
  В нём есть `?` (U3, U4, U10, U11, U25): у 5 из 17 микросхем точное совпадение невозможно в принципе.
  Ошибки VLM и эталона могут быть коррелированы.

## Как падает каждый движок

- **Текущий PP-OCRv3**: детектор не находит мелкий текст — 45/116 пустых ответов, в основном 0603.
  На `marking_img` ещё хуже, чем на цветной вырезке: CLAHE и увеличение мешают детектору.
- **PP-OCRv5/v6 (RapidOCR 3.10, PaddleOCR 3.7)**: находят почти всё, ошибаются в распознавании (`EIS` вместо `513`, `OIC`).
  Китайский словарь даёт иероглифы и `CO`/`00` на пустых корпусах; v6-small выдаёт ложное чтение на 19 из 40.
  Английская модель распознавания с детектором почти ничего не находит (4–34), но без детектора на вырезке корпуса даёт 51.
  Полный PaddleOCR 3.7 на Windows падает в oneDNN (`ConvertPirAttribute2RuntimeAttribute`), работает только с `enable_mkldnn=False`.
- **EasyOCR**: хорош на крупных цифровых кодах резисторов (58/80) и почти ничего не видит на микросхемах (1/17).
  Его уверенность не различает развороты: `513` вверх ногами уверенно читается как `E1S`.
  Поэтому при неизвестном развороте результат падает с 59 до 33, хотя хоть один поворот верен у 60.
- **Tesseract**: разметка страницы рассчитана на документ. Светлый текст на тёмном корпусе, пэды и шелкография дают мусор.
  Белый список не спасает: на 29 из 40 пустых деталей что-то «читается».
- **docTR / TrOCR**: документный детектор docTR пропускает всё.
  Распознаватели только строки (PARSeq, TrOCR) на вырезке корпуса читают светлые торцы резистора как буквы (`DIDICI`).
  Им нужна точная вырезка самой надписи, а это уже работа классификатора резисторов.
- **GOT-OCR 2.0**: без `stop_strings` зацикливается (`01C01C01C…`), с ним — 73/116.
  Галлюцинирует на пустых (`C`, `TOP`, `iN`).
- **PaddleOCR-VL**: хорошее распознавание (75), но на пустом корпусе отвечает фразой «The image is too blurry…» или одной цифрой: 27/40 ложных. Нужен фильтр ответов.
- **Florence-2-large**: самый быстрый (0,1 с на GPU) и не галлюцинирует (1/40).
  Но теряет символы на краях (`3N791A18` вместо `L03N791A1813`) и слаб на микросхемах.
- **Qwen3-VL-2B/4B**:
  - логотипы передаёт как символы: `▲107E`, `JH 133` у D25, `PE` вместо `FE1.1`;
  - на слабой лазерной маркировке путает символы (`RS2251 / T11S733`, `ZWG / 03K / CTUN`) и иногда добавляет правдоподобную третью строку (U3 `41052`);
  - пустые детали распознаёт уверенно: 0/40;
  - при неизвестном развороте теряет 10–11 точных: лучший поворот по уверенности не всегда правильный, хотя у 92–95 деталей правильный хотя бы один, а у резисторов — у всех 80;
  - 4B не лучше 2B, на ICs даже хуже.

## Предобработка, мульти-кадр, съёмка

- **Бинаризация (Otsu)** вредит всем: EasyOCR 59 → 33.
  **CLAHE** вредит детекторам (EasyOCR 59 → 43, PP-OCRv3 37 → 30) и Qwen (90 → 82 на `marking_img`).
  **Lanczos ×2 + нерезкое маскирование** («дешёвый SR») — 59 → 50.
  **Морфологическое закрытие 5×5 на ×2** — единственное, что помогает точечной матрице: EasyOCR 59 → 62, на резисторах 58 → 61.
  Настоящий SR (Real-ESRGAN и т. п.) не пробовал: VLM уже читают резисторы на 79/80, а ICs ограничены контрастом, а не разрешением.
  **Вывод: подавать VLM цветную вырезку без обработки.**
- **Мульти-кадр** (`frames.py`):
  - Стичер не сохраняет положения кадров, поэтому каждый `sources/*.jpg` найден в панораме сопоставлением шаблона (медианный NCC 0,96, минимальный 0,75).
  - Корпус целиком виден в 0/1/2/3/4 кадрах у 2/24/27/54/9 деталей. Перекрытие маленькое, и большие ICs часто видны только в одном кадре.
  - **Исходный кадр резче панорамы**: многополосное смешивание размывает. Qwen на `frame` даёт 92 против 90 на `raw`, Florence-2 — 63 против 59, EasyOCR — 60 против 59.
  - Медиана кадров (`fmed`) хуже одного резкого кадра: 89 против 92. Блики на 2–3 кадрах не уходят, а сдвиг в полпикселя мылит.
  - Голосование чтений raw+frame+fmed — 93: два-три кадра дают слабый ансамбль.
  - **Вывод для стичера:** для чтения маркировки вырезать детали из лучшего исходного кадра, а не из панорамы. Для этого стоит сохранять положения кадров в `report.json`.
- **Съёмка (железо).** Потолок на ICs (≈6/17) — контраст лазерной гравировки на матовом компаунде.
  Это не лечится движком; лечится светом:
  - **скользящий (raking) свет** под 10–30° с 2–4 сторон, по кадру на каждую сторону или переключаемые сегменты кольца — гравировка даёт тень и рельеф;
  - **кросс-поляризация** (поляризатор на свет и анализатор на объектив) убирает блики с выводов и глянца и поднимает контраст краски;
  - для ICs — отдельный проход с большим увеличением или телецентрикой и несколькими экспозициями (HDR), потому что контраст лазерной маркировки 5–10 %.
  Отдельный кадр под деталь также даёт настоящую многокадровую фьюзию вместо 2–3 случайных перекрытий.

## Рекомендация

1. **Второе чтение для всех групп — Qwen3-VL-2B-Instruct** на цветной вырезке (лучше из исходного кадра), с заданным разворотом.
   - Ожидаемо 90–93/116 точных против 28–37 сейчас: примерно ×2,5–3.
   - Резисторы 79/80, C/L/X 13/14 с точностью до символа, ложных на пустых нет.
   - Плата читается на GPU за ≈30 с (116 × 0,26 с), на CPU — за ≈15 мин, или ≈1 ч с 4 поворотами.
2. **Разворот** брать из эталона или из CAD (поворот посадочного места), а не перебирать 4 поворота по уверенности: это стоит 10–11 точных.
   Если разворот неизвестен — ограничить кандидатов (для чипов 0/180 вдоль длинной оси) или выбирать голосованием по нескольким изображениям.
3. **Резисторы.** Классификатору соседней сессии (55/80 leave-one-out) есть с чем сравниваться: Qwen3-VL-2B даёт 79/80 без обучения.
   Разумная схема: Qwen как основное чтение, классификатор и BOM как независимая проверка; расхождение — повод посмотреть глазами.
4. **Если GPU и PyTorch в проектном venv нежелательны** — заменить `rapidocr_onnxruntime` 1.2.3 на `rapidocr` 3.10 с моделями PP-OCRv5 server на `parts/`, а не на `marking_img`.
   Это 63/116 и 6/40 ложных; порог уверенности около 0,6 их срежет. Установка ≈300 МБ, только onnxruntime.
   Вариант на CPU — Qwen3-VL-2B в fp32 (≈7 с на чтение, та же точность).
5. **ICs** с текущей съёмкой ни один движок надёжно не читает (≤6/17 точно, CER ≥0,3).
   Для них нужен свет (см. выше), а пока — вывод «прочитано частично» и ручная проверка.
6. **Не брать**: Tesseract, docTR, TrOCR, MMOCR. PaddleOCR-VL и GOT — только с фильтром ответов (галлюцинации на пустых).
   Florence-2-large — запасной вариант, когда нужна скорость (0,1 с GPU / 4,5 с CPU), но он заметно хуже Qwen.

**Риски Qwen.**
- Изредка «дописывает» правдоподобную строку на нечитаемой ICs.
- Логотипы передаёт символами (`▲`, `H`).
- Ответ зависит от промпта. **Никогда не подставлять в промпт ожидаемое значение из BOM** — проверка превратится в эхо.
- 4 ГБ весов. Для GPU нужен PyTorch 2.14+cu130 (≈3,3 ГБ). Лицензия Apache-2.0.

### Как подключить к `ocrMarkings.py` (не сделано, по заданию код проекта не менял)

- Добавить в `ocrMarkings.py` опцию `--engine qwen`.
  Движок — класс как `engines/vlm.py`: `Engine("qwen3vl-2b").read(img) -> (lines, score)` с тем же промптом (`PROMPT`), greedy-декодированием и `score` = средней вероятностью сгенерированных токенов.
- На вход подавать цветную `parts/<ref>.jpg`, повёрнутую на `turn`; `enhance()` для Qwen не нужен (с ним 82 вместо 90).
  Маленькие вырезки увеличивать до короткой стороны ≥448 px (`pil()` в `vlm.py`).
- Запуск по выбору пользователя:
  - (а) поставить `torch` (cu130 или CPU) и `transformers>=5` в проектный venv;
  - (б) оставить отдельный venv и вызывать его подпроцессом, который пишет JSON `{ref: {lines, score}}` — так проектный venv не тяжелеет.
- `min_score` ≈ 0,5. Пустой ответ и `NONE` означают «нет маркировки».
- Вырезка из исходного кадра и голосование по кадрам потребуют сохранять в стичере положения кадров (сейчас их восстанавливает `frames.py`).

## Находки по эталону (`markings.json`)

- R44 (эталон `512`, turn 180, conf high): Qwen-2B, Qwen-4B, EasyOCR и PP-OCRv5 все читают `215`.
  Соседние R39/R43/R91 с тем же эталоном все читают `512` — R44 стоит проверить глазами и по BOM.
- U14/U16 `181D`: Qwen на исходном кадре читает точно, на панораме — `101D`/`L161D`. Это довод за вырезку из исходного кадра.
- C101/C102 `P? (2)`: Qwen уверенно читает `P6 ②` на всех четырёх — вероятно, `?` = `6`.

## Воспроизведение

```bash
cd research/ocr_engines
./mkvenvs.sh rapid3        # и tess / paddle / easyocr / doctr / hf; venvs/gpu — см. ниже
# venvs/gpu: py -3.13 -m venv venvs/gpu; pip install --index-url https://download.pytorch.org/whl/cu130 "torch==2.14.1+cu130" torchvision; pip install transformers accelerate opencv-python-headless numpy
venvs/rapid3/Scripts/python.exe frames.py                                   # кадры -> fusion/
../../venv/Scripts/python.exe bench.py rapid_v1 --blank                    # текущий базовый
venvs/rapid3/Scripts/python.exe bench.py rapid3 --variant v5-server --blank
venvs/easyocr/Scripts/python.exe bench.py easyocr_ --variant wl --sources raw,body --blank
venvs/gpu/Scripts/python.exe bench.py vlm --variant qwen3vl-2b --sources raw,body,frame,mimg,fmed --blank
venvs/gpu/Scripts/python.exe bench.py vlm --variant florence2-large --sources raw,frame --blank   # и got / paddleocrvl / qwen3vl-4b / trocr-base
BENCH_DEVICE=cpu venvs/hf/Scripts/python.exe bench.py vlm --variant qwen3vl-2b --sources raw --rots 0   # то же на CPU
../../venv/Scripts/python.exe fuse.py qwen2b-raw+frame vlm-qwen3vl-2b:raw vlm-qwen3vl-2b:frame vlm-qwen3vl-2b:fmed
../../venv/Scripts/python.exe score.py --print && ../../venv/Scripts/python.exe tables.py
```

Файлы:
- `common.py` — данные, источники, предобработка, свой `turn()`; `fold`/`agree` импортированы из `ocrMarkings.py`;
- `bench.py` — прогон движка, параметры `--threads`, `--prep`, `--rots`; продолжает прерванный прогон;
- `engines/*.py` — адаптеры;
- `frames.py` — мульти-кадр;
- `fuse.py` — голосование;
- `score.py` → `results/summary.{csv,json}` (с построчными чтениями в `detail`);
- `tables.py` → `results/tables.md`.

Сырые чтения лежат в `results/<tag>.jsonl`: по строке на деталь × источник × поворот.
