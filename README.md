# PcbAoiViewer

Самодельная AOI (автоматическая оптическая инспекция) печатных плат. USB-камера на 3D-принтере/ЧПУ снимает плату сеткой кадров, кадры сшиваются в одну панораму, на неё накладывается CAD (Pick&Place), дальше — проверка компонентов.

## Этапы

| # | Этап | Статус |
|---|------|--------|
| 1 | Съёмка сетки с ЧПУ (`capture.py`) | работает |
| 2 | Сшивка на одной высоте по координатам станка (`GridStitcher.py`) | **работает**, см. ниже |
| 3 | Вьювер панорамы (`BuildViewer.py`, Deep Zoom + OpenSeadragon) | работает |
| 4 | Высокие компоненты: параллакс и расфокус | **работает** в стеке: ортокоррекция по карте высот (`FocusStack.py`); в одиночной сшивке — `--parallax-regions` |
| 5 | Несколько высот: фокус-стекинг, карта высот, 3D | **работает** (`stackFocus.py`), см. ниже |
| 6 | Совмещение с CAD (плата из реестра → панорама) | **работает**: `importBoard.py`, `alignBoard.py`, слой «Board (CAD)» во вьювере; см. ниже |
| 7 | Инспекция компонентов | **начато**: маркировка прочитана в текст (`markings.json`) и сверена с BOM (`markingCheck.py`); чтение пока ручное или визуальной моделью, локального OCR нет; см. ниже |

## Сшивка (этапы 2–4)

Запуск и все опции: `venv/Scripts/python.exe stitchGrid.py --help`. Результат пишется в `out/<папка>/` (в `.gitignore`).

```bash
venv/Scripts/python.exe stitchGrid.py SocketTester2/captured_51.5
venv/Scripts/python.exe stitchGrid.py SocketTester2/captured_51.5 --parallax-regions --out out/captured_51.5_parallax
venv/Scripts/python.exe -m http.server 8765 --directory out/captured_51.5
```

Конвейер (`GridStitcher.py`):

1. **Плоское поле**: медиана всех кадров, размытая, используется как карта виньетирования.
2. **Калибровка**: одна матрица A на все кадры, положение кадра = A·(x_мм, y_мм). A оценивается по совпадениям AKAZE у соседей. Камера только сдвигается, поэтому поворотов и перспективы в модели нет.
3. **Пары**: все кадры с предсказанным перекрытием, включая диагональные. Фазовая корреляция по перекрытию, уверенность — NCC.
4. **Оптимизация**: взвешенный МНК по парам со слабой привязкой к координатам станка, Хубер плюс отбрасывание выбросов.
5. **Усиление**: коэффициенты на кадр и канал по перекрытиям (метод Brown & Lowe).
6. **Склейка**, по умолчанию `--blend multiband`. Детали берутся из кадра с ближайшим центром (шов Voronoi, ~12 px), низкие частоты (яркость, цвет) смешиваются в широкой полосе ~150 px. Режимы `voronoi`, `feather`, `hard` оставлены для сравнения.
7. **`--parallax-regions`** (по умолчанию выключено): там, где два выровненных кадра всё ещё локально сдвинуты больше чем на 10 px (фазовая корреляция в окнах), стоит высокий компонент. Такая область целиком берётся с одного кадра (ближайшего по центру и вмещающего её полностью), шов обходит её.

Результаты на Z=51.5 (полное разрешение, ~25–35 с):

- **Калибровка**: 77.66 / 77.35 px/мм (≈12.9 мкм/px), камера повёрнута на ~47° к осям станка, оси почти ортогональны (90.26°). Дисторсия объектива пренебрежимо мала. Механика точная: отклонение кадров от идеальной сетки — медиана 2.7 px, максимум 10 px.
- **Остатки по парам**: медиана 0.94 px, p90 2.8, максимум 5.8. Используется 190 пар из 215. Отброшенные — в основном коврик за краем платы: он на другой глубине и из-за параллакса сдвигается иначе.
- **Только по координатам** (`--no-refine`): медиана 2.4 px. Уже без ступенек, но примерно в 2.5 раза хуже.
- **Стабильность**: Z=50, 53, 47 и `captured5mm` дают медиану 0.9–1.1 px.

Почему так решено:

- **Voronoi, а не feather.** Обычное смешивание (feather) даёт двойные контуры на высоких компонентах.
- **Двухполосное смешивание (`multiband`).** Без него на швах видны ступеньки яркости, особенно на красных разъёмах. Компенсация усиления по кадру помогает слабо (разница в перекрытиях 8.9 → 7.8 уровня): различие в основном меняется по полю кадра (блики, угол освещения), а не от кадра к кадру.
- **Параллакс.** Камера стоит ~90 мм от платы (оценено по изменению масштаба с Z), поэтому верх компонента высотой ~3 мм смещается между соседними кадрами на ~25 px. Если шов проходит через надпись, символы слипаются: на тантале «1» и «0» в «107E» сливались в один знак. `--parallax-regions` это исправляет на обоих танталах и на конденсаторах 220-16.

### Известные ограничения

- `--parallax-regions` не видит компоненты с гладким верхом (индуктивности): там нечем мерить сдвиг. Координаты верха компонента всё равно смещены на 0–15 px, исправлено только чтение. Часть найденных областей — коврик за краем платы, на плату это не влияет.
- Верх высоких компонентов на Z=51.5 не в фокусе. Решено стеком высот, см. «Фокус-стекинг».

## Фокус-стекинг, карта высот, 3D (этап 5)

```bash
venv/Scripts/python.exe stackFocus.py "SocketTester2/captured_*" --ref 51.5
venv/Scripts/python.exe stackFocus.py "SocketTester2/captured_*" --ref 51.5 --scale 0.5 --out out/stack_s05
venv/Scripts/python.exe -m http.server 8765 --directory out/stack
```

Берутся папки по шаблону, число в конце имени — Z. По умолчанию Z от 50.0 с шагом 0.5 (`--zmin`, `--zstep`), это 11 слоёв. Конвейер (`FocusStack.py`):

1. **Опорная высота** (`--ref`, плата в фокусе) сшивается обычным `GridStitcher`: калибровка, пары, оптимизация, усиления, области параллакса.
2. **Регистрация высот.** Между высотами XY станка повторяется точнее 1 px, меняется только масштаб. Поэтому на каждую высоту хватает **одного** подобия (масштаб + сдвиг). Оно оценивается по AKAZE на 12 одноимённых кадрах из середины платы, берётся медиана. Масштаб строго линеен по Z: s = 1 + dz/D. Отсюда расстояние от центра проекции до платы **D ≈ 89.6 мм**. Центр кадра при этом сдвигается на ~6 px/мм по вертикали кадра: ось Z станка слегка наклонена к оптической оси. Высота, кадры которой не совпали с опорой (мало инлаеров), отбрасывается.
3. **Слои.** Кадры каждой высоты переводятся в геометрию опорных кадров и склеиваются с позициями, швами и усилениями опоры. Все панорамы слоёв совпадают по плоскости платы попиксельно.
4. **Глубина.** Мера фокуса — энергия лапласиана в ячейках 8×8 px полного разрешения (~100 мкм), размытая на ~12 px. Кривая фокуса широкая (~2 мм), поэтому Z лучшего фокуса — вершина МНК-параболы по 5 слоям вокруг максимума (лог меры), а не по трём. Ячейка считается измеренной, если (а) пик выше медианы по слоям на `--conf-min` и (б) пик в 4 раза выше «пола» панорамы (2-й перцентиль) — на гладком месте все слои на уровне шума, и относительный пик случаен (так получалось ложное пятно 2.5 мм на голой маске). **Опора — плата с учётом поля резкости камеры.** Плоскость резкости наклонена к сенсору: ~0.8 мм на ширину кадра по горизонтали и ~1.6 мм по вертикали кадра. Одна и та же точка платы резка при разных Z в разных кадрах. С одной плоскостью на всю панораму это давало узор ±0.5 мм по сетке кадров, в нём тонули резисторы 0.4–0.5 мм. Модель: Z платы = B(x, y) (кубика по панораме — изгиб платы) + F(u, v) (квадратика по координатам в кадре, одна на все кадры) + сглаженный местный остаток. Подгонка робастная по ячейкам платы: компоненты обрезаются сверху, коврик на 0.7+ мм ниже исключён. F одинаково сдвигает всё, что видно в этой точке кадра, поэтому высота = Z − B − F непрерывна через швы. Подгонка своей плоскости в каждом кадре пробовалась первой: в кадрах, где почти всё занято деталями, наклоны выходили неправдоподобными (до 2 мм на кадр), и на верхах деталей по швам появлялись ступеньки 0.5 мм. **Выше диапазона** (пик фокуса на верхнем слое, ~2% ячеек) известна только нижняя граница 55.0 − плата, и она следует за F. Каждая связная такая область (после замыкания 9×9) получает одну высоту — медиану границы: верх плоский, без ступеней по швам. **Иглы**: связные пятна выше 0.6 мм и меньше 0.5 мм² (меньше любой детали такой высоты; 0603 — 1.3 мм²) снимаются с измерения и заполняются заново. Это блики в переходных отверстиях и на припое, они давали ложный фокус на 2–4 мм. Высота = Z − плата. Дыры (гладкие верхи) заполняются нормированной свёрткой от измеренных ячеек. Широкие масштабы требуют плотной опоры со всех сторон, иначе ставится уровень платы: односторонняя опора размазывала высокие компоненты на плату ободком 0.7 мм.
5. **Ортокоррекция** (`--ortho-passes 1`). Точка на высоте h видна в кадре увеличенной в D/(D−h) раз относительно центра кадра. На слое Z это (D+dz)/(D+dz−h), так как его кадры уже приведены к опорному масштабу. Второй проход заново склеивает каждый слой: каждый кадр выбирается через `cv2.remap` по карте высот первого прохода (`GridStitcher.orthoWarp`). Верх высокого компонента во всех кадрах совпадает, шов через него больше не рвёт надпись, а сам компонент стоит на своём истинном XY. Области параллакса во втором проходе не нужны и выключены. Глубина пересчитывается по ортослоям.
6. **All-in-focus.** Каждый пиксель смешивает слои с весом exp(−(z_слоя − z_пикселя)²/2σ²), σ = 0.3 мм (`--depth-sigma`). Глубина берётся с заполненной карты, поэтому на гладких участках нет пятен от случайного выбора слоя.
7. **Слой маркировки** (`marking.jpg`, отключается `--no-marking`). Лазерная маркировка на матовом компаунде видна только под некоторыми углами к свету. В ближайшем к центру кадре она бывает почти не видна, а в соседнем, за 870 px от центра, читается чисто. Кроме того, самый резкий слой подчёркивает зерно компаунда, а не штрихи. Поэтому all-in-focus для чтения маркировки не годится, и для неё строится отдельная панорама:
   - **Детали** — связные области карты высот 0.45–4 мм. Открытие ~0.7 мм разделяет соседние микросхемы. Прямоугольник детали должен быть от 1.5 до 15 мм.
   - **Ракурсы.** Каждый кадр, где видно хотя бы 50% верха детали, на каждой высоте выбирается ортокоррекцией на холст. Оценка — контраст штрихов: полоса Гаусс 4 px − 25 px, делённая на местную яркость, std по верху детали без краёв. При полосе 2.5 px резкое зерно плохо освещённого кадра набирало почти столько же, сколько штрихи хорошо освещённого. От каждого кадра остаётся лучшая высота.
   - **Смешивание.** Кадр редко вмещает деталь целиком при шаге 10 мм, поэтому ракурсы смешиваются. Каждый подгоняется к лучшему сдвигом ECC, потому что после ортокоррекции верхи расходятся на 1–3 px и 8-пиксельные штрихи двоятся. Вес — (оценка / лучшая)⁸, у края кадра он плавно спадает. All-in-focus тоже участвует: он заполняет то, чего нет ни в одном кадре. Цвет ракурса приводится к среднему all-in-focus.
   - Деталь, где лучший ракурс не лучше all-in-focus, не меняется. Выбор по каждой детали (кадры, Z, оценки, доли) лежит в `marking.json` и `report.json`.

Результаты на SocketTester (Z 50.0–55.0, полное разрешение, `out/stack`):

- **Регистрация высот**: масштаб от 0.9835 (Z 50.0) до 1.0391 (Z 55.0), несогласие оценок по 12 кадрам ≤ 1.6 px.
- **Плата**: Z 51.18 мм (5-точечная парабола, раньше 51.44 по трём точкам). Поле резкости: размах 0.77 мм по ширине кадра (u) и 1.64 мм по v. Разброс измерений вокруг модели платы **0.10–0.11 мм** — оценка точности глубины на текстуре. Отсюда шумовые пятна 0.2–0.4 мм на голой маске.
- **Высоты**: танталы и 220-16 выше диапазона (верх ещё резкеет на 55.0): показаны плоскими на нижней границе ≈ 3.5–3.8 мм, реальная высота больше. То же с красными разъёмами. Резисторы и конденсаторы 0402/0603 видны как 0.4–0.6 мм, микросхемы — 0.7–1.2 мм. Но резистор 0.45 мм всего в 2–4 раза выше шума: для надёжного «есть / нет» нужна маска из CAD (порог по площади компонента, а не по ячейке). Измерено ~25% ячеек, ~21% — без текстуры, остальное заполнено.
- **Чтение надписей**: «107E 40A91» на обоих танталах и «220-16L P6» на паре конденсаторов чистые в all-in-focus. Без ортокоррекции один тантал читался как «1Q7E». Мультивысотный детектор `--parallax-regions` (`--parallax-z`) пробовал, вышло хуже: области становятся больше, чем помещается в один кадр, и снимаются.
- **Мелкий текст на плате** в all-in-focus так же резок, как на Z=51.5: ортокоррекция там не действует (h≈0).
- **Время**: 8.4 мин на полном разрешении (~40 с на слой за два прохода), ~4 мин на полуразрешении.

### Известные ограничения стека

- Слой маркировки на SocketTester (`out/stack_marking`, +40 с): 41 деталь, у 37 заменён верх, медианный контраст штрихов 162 → 190. QFN «NS2835 0DAA0 2042C» (кадр 50_60) раньше почти не читалась. Теперь она берётся в основном из 60_50 на Z 54.5 и читается целиком, так же как «PW534 23K64 CRD». Детали находятся по карте высот, без CAD. Поэтому низкая TSSOP в центре платы (ниже 0.45 мм по карте) пропущена, вплотную стоящие пары 220-16 идут одной деталью, а пара областей попадает на мат. После совмещения с CAD детали лучше брать из Pick&Place.
- Диапазон высот 0…3.6 мм над платой. Что выше 55.0 (разъёмы, стойки, винты), получает верхнюю границу. Мат за краем платы ниже 50.0 и тоже вне диапазона: он считается неизмеренным.
- Верх выше 55.0 мм не измерен, а лишь ограничен снизу. Чтобы мерить танталы и разъёмы, нужны слои до Z ≈ 57 (на ~6 мм над платой).
- Блики на металле дают ложные пики фокуса. В 3D это гасит медиана 9×9 по `mesh.bin`; на 2D-карте высот единичные выбросы видны.
- Стенки компонентов — интерполяция между верхом и платой (ячейка 100 мкм плюс размытие меры фокуса). Это 2.5D-рельеф, а не модель: под нависающим ничего нет.
- Для склейки берётся отдельная карта высот `FocusStack.orthoHeights()`: мат за краем платы и пятна внутри него обнуляются, отрицательные высоты обрезаются до 0. Без этого ошибка глубины на мате (−3 мм или ложные +4 мм) заставляла кадры брать пиксели за 20–40 px. Детали у края платы (например, светодиод возле 100_50) срезались прямой линией по границе кадра. Карта высот для 3D и отчёта не меняется. Кроме того, `GridStitcher.orthoWarp` возвращает маску: кадр отдаёт соседям пиксели, ортовыборка которых выходит за его край.
- Центр ортокоррекции принят за центр кадра. Реальный главный пункт не известен, ошибка одинакова для всех кадров, поэтому согласованность между кадрами не страдает, только абсолютный XY верха (до ~3 px на 3 мм).

### Вьювер стека

`index.html` — тот же вьювер; главный слой — all-in-focus. Добавлено:

- переключатель «all-in-focus / высота Z» с ползунком по слоям; клавиши `[` `]` — шаг по высоте, как фокусировка микроскопа, `f` — назад к all-in-focus;
- слой «marking» (клавиша `m`): панорама для чтения маркировки. Пунктиром показаны рамки деталей с основным кадром и Z, их можно выключить;
- наложение карты высот: цвета считаются в браузере из `height.bin`, диапазон 0…0.3–5 мм задаётся ползунком (по умолчанию 1.5 мм, чтобы были видны мелкие компоненты); неизмеренные (заполненные) ячейки бледные. Высота под курсором и в инспекторе по клику.

`3d.html` — three.js 0.160: сетка до 1.5 М вершин по `mesh.bin` (µm, int16), текстура all-in-focus 4k или 8k, вертикальный масштаб 1–8×, раскраска по высоте, освещение. Двойной клик — вращение вокруг точки.

Форма в 3D (`FocusStack.meshHeights`, `TEMPLATE_3D`): медиана 9×9. Для деталей выше 2 мм — серое открытие и замыкание 11×11 ячеек (~1.1 мм): срезают «крылья» сбоку корпуса (блики на паяном выводе тантала давали ложные 3.8 мм) и заливают узкие выкусы в корпусе (гладкий глянцевый торец без текстуры). Нормали считаются по поверхности, сглаженной 5×5 вершин: стенка в сетке — лесенка ячеек, и нормали треугольников давали полосы света. Стенки (крутизна по нормали) берут цвет края верха над собой (`wallUv` — uv самой высокой вершины в радиусе 3) из размытого мип-уровня. Фото стенки не содержит, а интерполяция между верхом и платой по тонким треугольникам давала вертикальную «гребёнку» оранжевого и синего.

Файлы стека: `focus.jpg` (all-in-focus, полное разрешение), `marking.jpg` + `marking.json` + `marking.dzi` (слой маркировки и выбор ракурсов по деталям), `layers/z*.jpg`, `z*.dzi` (тайлы слоёв), `height.npy` (мм над платой, ячейки 8 px), `height.bin` / `mesh.bin` (то же в µm int16 для браузера; в `mesh.bin` сглажено, −32768 — нет кадров), `height_color.png`, `focus_z.npy` (Z фокуса до заполнения), `board_z.npy` (местная плата), `measured.bin` (1 = измерено), `focus_layers.npy` (только с `--save-focus`: лог меры фокуса по слоям, чтобы подбирать шаг глубины без пересклейки), `confidence.png`, `report.json` (опорная сшивка + регистрация слоёв + статистика глубины + тайминги).

## Совмещение платы с панорамой (этап 6)

```bash
venv/Scripts/python.exe stitchGrid.py captured_51.5
venv/Scripts/python.exe alignBoard.py out/captured_51.5 boards/Antilatency.SocketTester.Main-r79
```

Модель — одно аффинное преобразование M: мм платы (Datum IPC-2581, Y вверх) → пиксели `panorama.jpg`. Камера только переносится, так что хватило бы подобия; аффинное поглощает ещё и анизотропию калибровки (77.66 / 77.35 px/мм).

1. **Грубо.** Плата рисуется из `board.json`: площадки своей стороны, отверстия, контур, корпуса. Её поле градиентов сравнивается с полем градиентов панорамы при 4 px/мм. Перебор: поворот 0…358° с шагом 2°, потом ±2° с шагом 0.25°, и зеркало. Края непокрытой (чёрной) области замаскированы. Точность около 1–1.5 мм.
2. **Точно — по отверстиям.** Каждое отверстие ищется у предсказанного места как кольцо края радиусом сверла. По найденным строится аффинное преобразование через RANSAC, поиск сужается: 2 мм (только металлизированные и неметаллизированные) → 0.3 → 0.15 мм (плюс переходные). Отверстия на уровне платы, поэтому параллакс высоких корпусов фит не тянет. Площадки не годятся: их края закрыты припоем и выводами; локальные окна по площадкам давали корреляцию около 0.14 и единицы инлайеров.

Результат на captured_51.5 + SocketTester.Main r79:

- поворот 42.41°, 77.49 / 77.50 px/мм, оси 89.87°, без зеркала;
- невязка по 207 отверстиям: медиана 1.7 px (**22 мкм**), p90 32 мкм;
- время — около 8 с.

В папку панорамы пишутся:

- `board.json` — данные платы плюс `align` (M, невязки, точки);
- `datasheets/` — копии MD-файлов даташитов;
- `parts/<ref>.jpg` — каждый компонент своей стороны отдельной картинкой, «прямо»: поворот компонента снят, вид сверху, контур + площадки + 0.5 мм поля, родное разрешение 77 px/мм (крупные разъёмы ужаты до 1400 px). На них потом читается маркировка. Надпись может оказаться повёрнутой на 180° (R3, X1), поэтому распознавать нужно в обеих ориентациях;
- `align_check.jpg` и `align_crops/<ref>.jpg` — для контроля на глаз.

Вьювер (`index.html`) сам находит `board.json` и показывает слой «Board (CAD)». После изменения `BuildViewer.py` страницу можно пересобрать без повторной сшивки: `venv/Scripts/python.exe BuildViewer.py out/captured_51.5`.

- Контуры компонентов окрашиваются по статусу установки или по группе. Статусы: fitted, NC (штрихом), optional, нет в BOM. Клик по легенде прячет группу.
- Площадки — отдельный слой, независимый от контуров. Подписи появляются при приближении и только у видимых компонентов.
- Есть поиск по позиционному обозначению, имени или номиналу.
- Клик по компоненту открывает карточку: номинал, коды маркировки резистора, даташит с разделами маркировки. Кнопка «frames» показывает исходные кадры этой точки.
- **Parts list** — все компоненты списком. Порядок: группа → строка BOM (по номиналу) → карточки с вырезкой из `parts/`. Счётчики есть у групп (с разбивкой по статусу установки) и у каждой строки BOM («×N»). Для резисторов рядом показано, какой код может стоять: 3 знака, 4 знака, EIA-96. Есть фильтры по группе, стороне, статусу и поиск, а также ползунок размера превью. Клик по карточке показывает компонент на панораме.
- **Diagnostics** (галочка или клавиша D) — HUD раз в секунду показывает:
  - fps и времена кадра (медиана / p95 / max);
  - время отрисовки оверлея;
  - тайлы OSD: сколько нарисовано на кадр, сколько загружено, время загрузки по Resource Timing, сколько в кеше;
  - длинные задачи главного потока;
  - зум, размер canvas, dpr;
  - догадку, где узкое место.

  Кнопка «copy last 60 s» копирует историю в JSON для разбора.

Оверлей рисуется из закешированных `Path2D` в координатах изображения: на кадр задаётся одно преобразование и вызывается несколько `stroke`, перерисовка идёт не чаще одного раза за кадр. Замер: 0.3–2.6 мс до переделки, доли миллисекунды после. По этому замеру основной лаг был, скорее всего, не в оверлее. Чтобы найти, где он на самом деле, нужен HUD в живом браузере: панель встроенного браузера скрыта и кадров не рисует.

`board.json` и `markings.json` загружаются с перепроверкой (`cache: 'no-cache'`), потому что скрипты их переписывают. Сам `index.html` после пересборки обновлять жёстко (Ctrl+F5).

Контур нарисован на уровне платы, поэтому верх высоких корпусов (танталовые конденсаторы, разъёмы) смещён от него параллаксом. Для стека с ортокоррекцией задуман запуск с `--image focus.jpg`; это не проверено, потому что других высот в этом клоне нет.

## Маркировка: чтение и сверка с BOM (этап 7)

```bash
venv/Scripts/python.exe markingSheets.py out/captured_51.5     # листы для чтения: marking_sheets/*.jpg + sheets.json
# чтение -> out/captured_51.5/markings.json
venv/Scripts/python.exe markingCheck.py out/captured_51.5      # сверка с BOM, вердикт пишется в markings.json
```

`markingSheets.py` раскладывает вырезки из `parts/` по группам BOM на листы шириной 1800 px. У мелких деталей рядом с вырезкой лежит её копия, повёрнутая на 180°. На листе подписано только позиционное обозначение, без номинала и ожидаемого кода, чтобы не подсказывать читающему. Площадки, отверстия и перемычки (35 шт.) пропускаются.

**Формат `markings.json`.** Для каждой детали:

- `present` — деталь на месте / место пустое;
- `lines` — текст построчно, сверху вниз, как нанесён;
- `turn` — на сколько градусов по часовой повернуть вырезку, чтобы текст читался;
- `conf` — уверенность: high / medium / low;
- `note` — примечание.

**Как читалось.** Локального OCR нет: Tesseract не установлен, а EasyOCR или Paddle тянут torch и модели. Поэтому прочитано визуальной моделью (Claude) по листам. Тусклая лазерная маркировка микросхем читалась по вырезкам с CLAHE в трёх поворотах. Итог по 233 деталям:

- на 116 прочитан текст;
- 8 мест пустые;
- у микросхем часть строк с `?` или `conf: low`;
- не прочитаны U5, U15, U17, U18, U19, U28 и Q2: маркировка не видна при этой высоте и освещении.

`markingCheck.py` декодирует коды резисторов (EIA-96, 3 и 4 знака, R-нотация) и сравнивает с номиналом из BOM с допуском 0.5 %. Наличие детали сверяется со статусом установки. Результаты на SocketTester.Main r79 / captured_51.5: ok 82, info 144 и 7 находок.

| Деталь | Находка |
|---|---|
| R91, R92 | нанесено `512` = 5.1 кОм, в BOM 1.5k (на R41 и R94 из той же строки — `18B` = 1.5 кОм, как надо) |
| R26_DC_REG | нанесено `36C` = 23.2 **к**Ом, в BOM «23.2» (= 23.2 Ом); скорее ошибка в BOM: у пары R26_DC_5V 1.96k стоит `29B` |
| J29, TO_MAIN, SW1 | в BOM установлены, на плате места пустые (SMA, IDC-40, DIP-переключатель) |
| USBP2 | в BOM NC, на плате стоит 4-контактная гребёнка |
| D9 *(не автоматом)* | нанесено `B320A`, в BOM B330A-13-F — другой диод (2 А / 20 В вместо 3 А / 30 В); у диодов и микросхем `markingCheck.py` пока только показывает текст (`info`), сверка с таблицей маркировки из даташита — следующий шаг |

### Локальный OCR как второе, независимое чтение

```bash
venv/Scripts/python.exe ocrMarkings.py out/captured_51.5                  # ~6 мин на 233 детали
venv/Scripts/python.exe ocrMarkings.py out/captured_51.5 --compare-only   # только пересравнить после правки markings.json
```

Движок — RapidOCR (`rapidocr_onnxruntime`, PaddleOCR PP-OCRv3 det + rec в ONNX, CPU). Модели (13 МБ) лежат в самом пакете, при запуске ничего не скачивается. Для каждой детали:

1. **`marking_img/<ref>.jpg` — картинка для чтения.** Вырезка в сером (канал L из Lab), лёгкое размытие, CLAHE (локальный контраст: бледная лазерная маркировка на тёмном корпусе), увеличение до ~420 px, поворот на `turn`, чтобы текст стоял прямо. Именно по такой обработке читалась маркировка микросхем. Вьювер показывает эту картинку рядом с исходной вырезкой.
2. **OCR в четырёх поворотах**, не глядя на первое чтение. Берётся поворот с лучшим средним score (≥ 0.5). Строки собираются по вертикальному центру рамок.
3. **Сравнение с первым чтением** после склейки похожих символов (O/0/D, I/L/1, S/5, B/8, Z/2, G/6). Вердикты:
   - `same` — совпадает;
   - `close` — расходится в одном символе;
   - `partial` — каждая строка OCR есть среди прочитанных;
   - `differs` — расходится;
   - `ocr-only` — OCR нашёл текст, которого нет в первом чтении;
   - `none` — оба ничего не прочитали.

   Если лучший по score поворот не совпал, а другой совпал, это записывается в `otherTurn`.

Итог на captured_51.5: same 28, close 11, partial 10, differs 67, ocr-only 2, none 115; у X1 и ещё пяти деталей совпал другой поворот.

**Что OCR умеет и чего нет:**

- Крупный текст он читает: 1206-резисторы, `B540C`, `4R7`, `220-16L`, кварцы, `PN534` на TCA9534.
- Точечные коды 0603 (`01C`, `01A`) он почти не видит: детектор их не находит. Пробовал распознавание без детекции по полосе корпуса и по плотной рамке текста — ни одного совпадения на 70 резисторах. Для них нужен свой классификатор под этот шрифт (алфавит маленький, шрифт один).
- Перевёрнутые на 180° коды он иногда читает задом наперёд (`215` вместо `512`).
- Как контроль OCR полезен: у **D9** он независимо прочитал `8320`, что подтверждает B320A вместо B330A. У **R91** он прочитал `152` против `512` при первом чтении. По картинке это `512`, но такие расхождения стоит просматривать.

Во вьювере:

- в «parts list» под каждой вырезкой показаны: прочитанный текст построчно, вердикт сверки с BOM и отметка OCR (`OCR ✓`, `OCR ✓ part`, `OCR ✓ (turned …)`, `OCR: <текст>`). Есть фильтр «problems / ok / unread / marking read / OCR differs / OCR agrees», поиск идёт и по прочитанному тексту, и по тексту OCR;
- в карточке компонента:
  - строки «marking read» и «OCR» (score, поворот, вердикт);
  - две картинки рядом: «crop as cut» и «reading image» — то, из чего получена надпись;
- галочка «findings» подсвечивает находки красным на панораме.

### Свой распознаватель кодов резисторов (третье чтение)

```bash
venv/Scripts/python.exe resistorDataset.py add out/captured_51.5 --auto       # метки там, где эталон и Qwen совпали
venv/Scripts/python.exe resistorDataset.py add out/captured_51.5              # метки = эталонное чтение (conf high/medium)
venv/Scripts/python.exe resistorDataset.py correct out/captured_51.5 R91 512  # одна деталь, правильный код
venv/Scripts/python.exe resistorDataset.py correct out/captured_51.5 R41 -    # пример негоден (грязь, не в фокусе)
venv/Scripts/python.exe resistorDataset.py synth --sheet out/synth_sheet.png  # синтетические символы + лист «живые/синт.»
venv/Scripts/python.exe resistorDataset.py stats                              # сколько каких кодов и символов
venv/Scripts/python.exe readResistorCodes.py out/captured_51.5                # -> markings.json parts[ref].resistorCode
venv/Scripts/python.exe readResistorCodes.py --eval                           # точность по шагам, out/resistor_codes_eval/
```

RapidOCR не видит точечные коды 0603, поэтому для резисторов сделан свой распознаватель: только numpy + OpenCV, CPU, ~0.1 с на деталь, обучение ~1 с при каждом запуске (модель — сами примеры). Код: `ResistorCodes.py`, синтетика — `SynthGlyphs.py`.

1. **Корпус.** Тёмный коричневатый корпус отделяется от синей маски по R−B (порог посередине между краем вырезки и центром — баланс белого в кадрах разный), закрытие/открытие, затем рамка обрезается до строк и столбцов, которые корпус покрывает хотя бы наполовину (отрезает куски площадок). Для полоски ориентации берётся ещё и «контекст»: те же столбцы плюс 0.6 высоты корпуса сверху и снизу.
2. **Символы.** White top-hat (тонкие штрихи остаются, широкие блики площадок уходят) + Otsu, строка текста — медиана верха и низа компонентов высотой с символ; подчёркивания, точки и толстые блики выкидываются. Шрифт **не моноширинный** (`1` узкая и стоит вплотную к соседям), поэтому символы — это столбцы с чернилами; для гипотезы из n символов слишком широкий столбец режется по самому слабому месту, лишний сливается с соседом или отбрасывается с края (блик на площадке). Цена разрезов и слияний идёт в оценку.
3. **Классификатор.** Символ нормируется в 24 × 32 (фон гасится маской его чернил), признаки — HOG + грубая сетка яркости + ширина; по каждому классу — среднее расстояние до двух ближайших примеров, softmax. Аугментация: сдвиг, масштаб, поворот ±3°, размытие, контраст. Отдельный класс-«отказ» — те же символы вверх ногами: так код в неправильном повороте получает низкую оценку. 0 1 2 5 8 H S X Z при повороте остаются собой, 6 ↔ 9 (`512` вверх ногами читается как `215`) — их в «отказ» не кладём. `3` вверх ногами похожа на `E`, но оставить её в «отказе» выгоднее (+2 детали: повороты `333`, `223`, `513`), `E` в коде бывает только последней.
4. **Полоска ориентации.** У части 3-значных кодов одной серии под средней цифрой короткая полоска (`220`, `272`, `333`, `621`). Ищется на контексте по строкам открытого top-hat: строка яркая под средним символом (его столбцы из разреза на 3) и тёмная под крайними, толщина 0.11–0.3 высоты символа, начало не дальше 0.15 высоты от строки, шириной 0.3–0.9 высоты, дальше тёмные строки (блики на крае корпуса тоньше и дальше). Полоска снизу — +1 к оценке поворота, сверху — −1 (`BAR_PRIOR`); в ячейки символов она не попадает.
5. **Грамматика.** Перебираются все допустимые коды длины 1, 3 и 4: EIA-96 (`01C`…`96F`, буквы ZYRXSABHCDEF), 3- и 4-значные, R-нотация (`R10`, `4R7`, `22R0`, `R200`), `0`. Код = максимум суммы log-вероятностей символов с маленьким априори (3 знака чаще 4, код с ведущим нулём, кроме EIA-96, маловероятен). Повороты: 0 и 180°, у сборок резисторов (`*ARRAY*`, текст поперёк) — все четыре. Побеждает гипотеза (поворот × длина) с лучшей средней log-вероятностью минус цена сегментации плюс полоска.

**Синтетические символы** (`SynthGlyphs.py`, `resistorDataset.py synth`). Каждый символ — набор отрезков 7-сегментного вида (у `B`, `D`, `R`, `X`, `Y`, `Z` свои), нарисованный рядом лазерных точек, размытый и нормированный как настоящая ячейка. Вид меряется по живым ячейкам: верх/низ и ширина символа, толщина штриха, яркость символа и фона; шаг точек, размытие и толщина подбираются так, чтобы синтетика известных классов легла ближе всего к живым (в признаках классификатора). Каждый символ дрожит: штрих, шаг, ширина, наклон ±2.5°, яркость, шум. Лежат в `dataset/resistor_codes/synth/` (`manifest.csv` с origin `synth`, `params.json`), 40 на класс, 22 класса. В обучение идут только для классов, у которых живых символов меньше 10 (`SYNTH_FOR`, `SYNTH_RARE`, `SYNTH_N` = 20, `SYNTH_DIST` — множитель расстояния до синтетики); в оценку не попадают никогда. Лист «живые слева, синтетика справа» — `--sheet`.

**Автометки** (`add --auto`): деталь получает метку без человека, только если эталонное чтение (`lines`) и Qwen (`vlm.lines`) совпадают после склейки похожих символов (`ocrMarkings.agree == "same"`), в одном повороте, и код допустим по грамматике; origin `auto`. Расхождения уходят в `dataset/resistor_codes/review.csv`, а не в датасет. BOM в решении о метке не участвует.

В `markings.json` пишется только `parts[ref].resistorCode = {code, score, margin, runnerUp, turn, chars, bar, agree, bom, value}`: `score` — среднее геометрическое вероятностей символов (0..1), `margin` — отрыв по log-оценке от второго кода, `turn` — поворот от `parts/<ref>.jpg`, `chars` — лучший класс каждой ячейки без грамматики, `bar` — полоска в этом повороте (1 снизу, −1 сверху, 0 нет), `agree` — сравнение с первым чтением (`same | differs | none | unread`), `bom` — код против номинала BOM, как в `markingCheck.py` (`ok | mismatch | -`). Деталь, которая есть в датасете, читается моделью **без её собственных примеров** (leave-one-out; `--with-self` отключает).

**Датасет `dataset/resistor_codes/`** (в git, ~1.8 МБ, из них синтетика ~0.5): `manifest.csv` (image, bodyBox, label, source, board, ref, footprint, turn, origin = auto | reference | manual, split, status, segCost, note, added), `codes/<source>/<ref>.png` — вертикально стоящий серый корпус с контекстом сверху и снизу, `bodyBox` — сам корпус в нём; `chars/<source>/<ref>_<i>.png` — вырезанные под метку символы, для глаза; `review.csv`; `synth/`. Поворот сборок подбирается моделью, обученной на остальных деталях. Split по детали: crc32(source/ref) % 5 == 0 → val. `status`: `ok` — идёт в обучение; `badseg` — разрез под метку потребовал дорогих слияний/разрезов, только для оценки; `noline` / `nobody` — текст или корпус не найден; `dropped` — помечено руками. Строки `manual` (`correct`) повторный `add` не трогает. **Как растить:** новая панорама → эталонное чтение + `vlmMarkings.py` → `add --auto` → просмотреть `review.csv`, нужное внести через `correct`; при новых классах — `synth` заново.

**Точность на captured_51.5** (80 размеченных резисторов, одна плата; все 80 — `auto`, Qwen совпал с эталоном везде, `review.csv` пуст). Leave-one-part-out по живым деталям, оба поворота, сбой сегментации = ошибка; «уверенно» — score ≥ 0.5 и margin ≥ 1:

| шаг | верно | поворот = эталону | уверенно / из них ошибок |
|---|---|---|---|
| до (без полоски, без синтетики) | 55/80 = 69 % | 72/80 | 46 / 6 |
| + полоска ориентации | 55/80 = 69 % | 72/80 | 46 / 6 |
| + синтетика для редких классов (итог) | 55/80 = 69 % | 72/80 | 40 / 3 |
| вариант: синтетика для всех классов | 53/80 | 72/80 | 40 / 4 |
| вариант: `3` не в «отказе» | 52/80 | 72/80 | 40 / 6 |
| автометки вместо эталонных | те же 80 меток — без изменений | | |

- train (65) → val (15): 13/15. Вся цепочка от `parts/` против первого чтения: same 55, differs 24, unread 1; в `compare/Resistors.html` — same 55, close 10, differs 15.
- Полоска нашлась на 5 деталях (R15, R16 `220`, R17 `272`, R87, R88 `333`), всегда снизу в эталонном повороте — ни одного противоречия. R98 `621` не найдена (`62` слипаются, средняя ячейка выходит не та), R72 `223` — слишком бледная. Эти 5 деталей и без неё читались верно, поэтому на точность она не повлияла; она страхует поворот там, где `1` нет (`333` и `220` симметричны почти целиком).
- Синтетика: модель, обученная только на живых символах, узнаёт 86 % синтетических символов известных классов (518/600), то есть вид близок, но не тот же. Число верных деталей не изменилось (исправились R65, R91, сломались R43 `512` → `215` и R81), зато уверенных ошибок вдвое меньше. Главное, ради чего она есть, — коды с E F H S X Y Z и редкими цифрами — на этой плате проверить нечем.
- Посимвольно (разрез под длину метки, leave-one-out): `0` 48/60, `1` 53/64, `2` 20/24, `3` 13/16, `5` 8/11, `A` 12/12, `C` 18/21, `D` 5/5, `B` 5/7, `R` 3/4, `7` 3/3, `6` 2/5, `8` 1/5, `4` 1/2, `9` 0/1.

Ошибки (`out/resistor_codes_eval/failures.jpg`):

- редкие символы: `84C` → `89C`, `76C` → `701`, `29B` → `862`, `R200` → `R70`, `1000` → `110`;
- блик на краю корпуса, принятый за `1` (`512` → `1512`, `621` → `6211`, `184` → `2184`);
- поворот: коды из 0/1/2/5/8 почти симметричны, решает флажок у `1` (`512` → `215`, `01C` → `501`, `05C` → `15C`);
- сборки резисторов (`101` → `550`, R21 текст не найден): 10 штук, шрифт мельче.

Что не обобщится: всё обучено на одной плате, одном освещении, одной камере и одном масштабе (~77.5 px/мм), почти все примеры 0603 одного производителя; полоска — признак одной серии. Другой шрифт (не 7-сегментный), другой цвет корпуса или маски (порог R−B рассчитан на синюю маску и чёрный корпус) потребуют новых примеров, а может, и правки поиска корпуса. Параметры (и вид синтетики) подбирались на тех же данных, оценка немного оптимистична.

Во вьювере результат классификатора показан так:

- в «parts list» у резисторов — отметка `code ✓` при `agree = same` и `code: <code>` при `differs` (красным, если ещё и `bom = mismatch`);
- в карточке — строка «resistor code»: code, score, margin, runner-up, turn, value, вердикт;
- в списке есть фильтр «code differs».

### Qwen3-VL-2B: второе чтение локальной VLM (основное автоматическое)

По обзору `research/ocr_engines/REPORT.md` лучший локальный читатель — Qwen3-VL-2B-Instruct (Apache-2.0, 4 ГБ весов). Он работает в **отдельном venv**, проектный `venv/` остаётся лёгким:

```bash
venv/Scripts/python.exe vlmMarkings.py out/captured_51.5    # ~40 с на 233 детали на RTX 5080 (вместе с загрузкой модели)
```

- `vlmMarkings.py` (проектный venv) собирает задания из `markings.json`: `parts/<ref>.jpg` и поворот `turn` из первого чтения. Дальше он запускает подпроцессом `vlmWorker.py` в VLM-venv и пишет `parts[ref].vlm = {lines, score, turn, agree, model}`. `agree` считается как у OCR. Обмен идёт через `vlm_jobs.json` / `vlm_results.json` в папке панорамы.
- VLM-venv — `--python` или `AOI_VLM_PYTHON`. По умолчанию это `research/ocr_engines/venvs/gpu`: torch 2.14 cu130 + transformers 5.20, ≈3.4 ГБ. Веса — `--hf-home` / `HF_HOME`, по умолчанию `research/ocr_engines/cache/hf`; если модель там есть, запуск идёт офлайн. Как собрать свой venv, написано в шапке `vlmMarkings.py`. На CPU — около 7 с на деталь.
- Вход — цветная вырезка без обработки: CLAHE модели вредит. Короткая сторона увеличивается до ≥ 448 px, декодирование жадное. Промпт фиксированный и **никогда не содержит ожидаемого значения из BOM**, иначе проверка превратится в эхо.

Результат на captured_51.5:

- same 91, close 10, partial 2, differs 13, ocr-only 5, none 112;
- **все резисторы совпали**;
- расходятся в основном микросхемы с бледной лазерной маркировкой (U1–U4, U10, U11, U16, U25). Там и первое чтение помечено `low` / `?`, так что истины нет ни у кого.

Чего ждать от VLM:

- Логотипы VLM передаёт символами: `▲07E`, `H133`, `PE` вместо `FE1.1`.
- «ocr-only» на пустых местах берётся с соседей, а не выдумывается:
  - вырезка пустого J29 захватывает кварц X1 — чтение `32.0 / AK9F`;
  - у светодиодов EXT, TU, USB2 в кадр попадает шелкография.

  Надёжнее было бы вырезать по корпусу, а не по посадочному месту с полем.
- Чтение VLM подтвердило D9 = `B320A` (VLM: `8320A`).
- Чтение VLM поправило эталон: у R44 был неверный поворот. Код `512` прочитан правильно, но записан с `turn: 180` вместо 0; исправлено в `markings.json`.

Во вьювере:

- в «parts list» — отметка `VLM ✓` / `VLM ≈ …` / `VLM: …` и фильтр «VLM differs»;
- в карточке — строка «VLM» (текст, score, поворот, модель).

## Данные платы из реестра (этапы 6–7)

Источник — сервер реестра сборок (Antilatency.Electronics.Registry.Server): у сборки кнопка «Download all» = `GET /api/builds/<key>/artifacts.zip`. Из архива берётся только нужное для инспекции, остальное (Gerber, ODB, сверловка, отчёты) пропускается.

```bash
python importBoard.py <artifacts.zip | папка сборки>     # -> boards/<проект>-r<rev>/
```

В папке `boards/<проект>-r<rev>/`:

- `board.json` — всё одним файлом, схема в шапке `BoardData.py`:
  - контур платы и отверстия (для совмещения с панорамой);
  - компоненты из IPC-2581: сторона, X/Y/поворот, корпус, высота, контур корпуса и площадки с номерами, именами пинов и цепями, а также позиция из Pick&Place для сверки;
  - строки BOM:
    - статус установки `fit`: `fitted`; `nc` — место должно остаться пустым; `optional` — «X/NC», на части плат стоит, на части нет; `none` — компонента нет в BOM (площадки, тестовые точки);
    - тип (группа и подгруппа, правила те же, что на сервере);
    - номинал: Ω/F/H/Hz, напряжение конденсатора, для резисторов — возможные коды маркировки (3 знака, 4 знака, EIA-96);
    - найденный даташит: Excursus и разделы маркировки, ordering и корпуса из MD (раздел целиком, с номером страницы).
- `export/` — исходные файлы: BOM, Pick Place, IPC-2581, WireList, STEP, PDF (сборочный чертёж, 3D, схема), `build.json`.
- `datasheets/` — копии найденных MD-файлов из библиотеки Antilatency.Electronics.Datasheets вместе с их картинками, пути как в библиотеке. Папка самодостаточна: библиотека нужна только при импорте.

Просмотр: `python -m http.server 8600` в корне репозитория, затем `http://127.0.0.1:8600/boardView.html?board=boards/<проект>-r<rev>`. Плата рисуется в SVG: верх и низ (низ отзеркален, вид снизу), цвет по статусу установки или по группе, клик по пункту легенды прячет группу. Поиск принимает позиционное обозначение, имя или номинал («10k»). Карточка компонента показывает номинал, коды маркировки и разделы даташита с картинками.

Координаты: мм от Datum IPC-2581, Y вверх, вид сверху, нижняя сторона **не** зеркалится. Pick&Place с IPC-2581 совпадают до 1 мм; расходятся только компоненты, у которых точка привязки не в центре (R93, разъёмы MICRO-MATCH). Для инспекции центр корпуса брать по `bb` / `outline`, а не по X/Y.

Модули (только stdlib):

- `Ipc2581.py` — `parse` и `resolve` из `tools/ipc2581.py` сервера без изменений; правки переносить в обе стороны.
- `AltiumExport.py` — архив и папка сборки, BOM (ANSI), Pick Place (фиксированная ширина, многострочные описания; старый CSV тоже читается), WireList.
- `Components.py` — NC/optional, разбор номиналов, коды маркировки резисторов, тип компонента.
- `Datasheets.py` — библиотека даташитов, подбор документа по строке BOM (как на сервере, с ручными связями из `data/datasheet-links.json` сервера), Excursus, разделы по заголовкам, копирование.
- `BoardData.py` — сборка `board.json`; `loadBoard`, `componentsOf(board, group="Resistors", side="top")`.

Маркировка в MD не имеет отдельного поля. Она лежит под заголовками вида «Top marking», «Marking Information», «Package Marking Information», «Date Code Key», а у TI — в колонке Device Marking таблицы Package Option Addendum. Поэтому `sections` отдаёт раздел целиком, а расшифровку (код продукта, год/неделя) нужно делать уже поверх этого текста.

Проверено на SocketTester.Main r79 (та же ревизия, что `captured_51.5`):

- 324 компонента, 107 строк BOM;
- 28 строк с даташитом — ровно как на сервере, отличий в подборе и классификации нет;
- 10 даташитов с отдельным разделом маркировки.

## История решений

- **2026-10-17.** Попарная сшивка `AffineStitcher` заменена сшивкой по координатам станка с глобальной оптимизацией (`GridStitcher.py`) и вьювером Deep Zoom. Выбрана высота Z=51.5 — максимум резкости по Laplacian/Tenengrad.
- **2026-10-18.** Добавлены:
  - компенсация усиления;
  - двухполосное смешивание — стало режимом по умолчанию, убрало ступеньки яркости на швах;
  - инспектор исходников по клику во вьювере;
  - переключатель `--parallax-regions`. Он выключен по умолчанию, пока не проверен на других высотах и платах. Первая версия детектора по разнице яркости не подошла: шум по всей плате, всё слипалось в огромные области. Рабочая версия — локальный сдвиг фазовой корреляцией, порог 10 px.
  - фокус-стекинг по 11 высотам (`FocusStack.py`, `stackFocus.py`): одно подобие на высоту вместо пересшивки каждой, карта высот по фокусу, ортокоррекция вторым проходом, all-in-focus, вьювер слоёв и 3D (`3d.html`). Ортокоррекция вместо областей параллакса: области приходится брать целиком из одного кадра, и на высоких слоях они перерастают кадр.
  - слой маркировки (`FocusStack.markingLayer`). Маркировка QFN «NS2835» в all-in-focus почти не читалась, хотя в соседнем кадре была чёткой. Отдельный слой выбран, чтобы не трогать all-in-focus: для маркировки нужен другой ракурс, и его яркость и блики на основной панораме выглядели бы пятнами. Сначала требовался кадр, вмещающий деталь целиком. Так почти у каждой детали оставался один кадр, и у этой QFN как раз не тот. Поэтому ракурсы теперь смешиваются по оценке.
